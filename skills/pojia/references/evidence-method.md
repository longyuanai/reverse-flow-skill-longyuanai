# 从原始事实到可核验结论

## 专家会补上的工作

用户给的题目经常省略失败条件、版本身份和竞争解释。先补这三项，通常比增加工具更有价值：

- 这个结论何时会被推翻？哪个最小输入能区别两个解释？
- 我们分析的是哪个构建、配置、架构和运行状态？证据是否绑定同一份文件？
- 看到的是声明、静态可达路径、实际执行，还是模型猜测？
- 哪些事实因为工具覆盖不足而未知？“未观察到”不能改写成“不存在”。
- 漏洞候选还需证实输入可控、实际可达、影响和根因；普通代码特征不足以成立。

## 从什么原始材料开始

| 问题 | 优先原始材料 | 不足以独立证明的材料 |
|---|---|---|
| 原生函数行为 | 原始二进制、架构、指令字节、调用者/被调用者、重定位 | 一张伪代码截图 |
| .NET 函数行为 | PE/CLI 字节、MVID、方法 token、原始 CIL 与分支/异常表 | 反编译后的 C# 名称 |
| Android 行为 | 原 APK/DEX、Manifest、签名/版本、具体调用链 | 应用介绍页 |
| Web/API 行为 | 授权环境中的原始请求响应、路由代码、网关与后端日志关联 | 前端按钮、接口名称 |
| 补丁影响 | 两个构建的字节、构建选项、真实差异、同一输入下的行为 | 版本号或发布说明 |

抓包、内存、日志可能含密钥或客户数据。保留完整原件于用户控制的 case，不自动纳入 Git、上传外部服务或对外报告；导出副本按用户要求脱敏并注明处理。

## 方法选择

1. 从入口/调用者确认目标函数在本题中的作用，避免孤立解读一个名字。
2. 跟踪输入来源、关键运算、条件分支、输出消费者和错误路径。
3. 对整数明确位宽、符号、移位、溢出规则和字节序。CIL `shr` 与 `shr.un` 不同；乘加的模运算不能靠 Python 的无限精度整数自然得到。
4. 反编译结果视为解释层，回看原始指令、常量、分支目的地及其字节位置。
5. 写下可失败的预测，再测试。覆盖成功路径、拒绝路径和边界值；随机样本固定 seed 并保留输入列表。
6. 使用负对照：改变一个重要条件或常量，测试应能区分。仅将输出替换成固定答案的测试容易假通过。
7. 不需要动态执行就能回答的问题，不运行未知样本。

## 能证明到哪一层

| 证据 | 可以支持 | 不能单独支持 |
|---|---|---|
| SHA-256 一致 | 两份内容身份一致（通常假设下） | 内容无害或来源可信 |
| `--version`/启动成功 | 可执行程序能启动 | 某个分析器真的工作 |
| MCP initialize + tools/list | 此连接的协议握手和目录可读 | 每个工具都能分析真实目标 |
| REA CLI 与 MCP 同结果 | 两种适配入口一致 | 独立解析器交叉证明 |
| 原始 CIL 与 Reflection 读取字节一致 | 指令来源与选定方法对应 | 所有运行时行为均已验证 |
| 重建与原程序在固定语料一致 | 已测输入上的行为等价 | 全输入、所有异常/并发路径等价 |
| 独立复核者能重跑 | 记录足以复现，发现作者遗漏的机会增加 | 复核者意见本身保证正确 |

## 报告中的每条关键结论

用以下结构组织，不强制生成表格文件：

`命题 → 证据定位 → 推导 → 区别性验证 → 结果 → 残余不确定性`

例：先提出“长度字段采用小端序”，再给出读取指令与文件偏移，用高低字节互换的输入区别另一种解释，最后报告差分结果与尚未覆盖的长度范围。

静态结论、推断和运行观察应分别标记。高置信度不等于已证明；没有运行的步骤明确写“未执行”。
